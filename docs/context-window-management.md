# Context Window 관리 설계

## 배경

AI 면접에서 대화가 길어질수록 AI 호출 시간이 급격히 증가한다.

| 대화 길이 | `chat` 평균 시간 | `chat` 최대 시간 |
|-----------|-----------------|-----------------|
| 짧은 대화 (5턴 이내) | 7.65초 | 7.65초 |
| 긴 대화 (10턴 이상) | 9.98초 | 12~13초 |

원인: 모든 프롬프트가 전체 대화 히스토리를 무제한으로 포함한다. 대화가 30턴을 넘어가면 프롬프트 토큰이 수만 개에 달하고, AI 응답 시간은 토큰 수에 비례하여 증가한다.

### 무제한 히스토리 사용 지점

| 호출 지점 | 메서드 | 히스토리 사용 |
|-----------|--------|-------------|
| 메인 응답 | `claudeAiClient.chat/streamChat` | `List<ChatMessage>` 전체 전달 |
| 비동기 평가 | `InterviewEvaluationService.buildEvalPrompt` | 전체 히스토리를 문자열로 직접 조합 |
| 종료 피드백 | `InterviewServiceImpl.buildConversationText` | 전체 메시지 연결 (세션당 1회) |

### 현재 제한되는 것 vs 제한 없는 것

| 제한 있음 | 제한 없음 |
|----------|----------|
| 문서 길이 (1500자) | 대화 히스토리 |
| 채용공고 길이 (1500자) | 메시지 개수 |
| | 메시지 길이 |
| | 평가 프롬프트 크기 |
| | 피드백 대화 크기 |

## 해결 방안 비교

### 방안 1: 순수 Sliding Window

```
[System Prompt] + [첫 질문(예약)] + [최근 N턴 원문]
```

오래된 메시지를 버리고, 토큰 budget 내에서 최근 메시지만 유지한다. 첫 메시지(AI 첫 질문)는 면접 맥락을 위해 항상 포함한다.

| 항목 | 내용 |
|------|------|
| 구현 복잡도 | 낮음 — `TokenEstimator` 유틸리티 1개 |
| 추가 AI 호출 | 없음 |
| 추가 인프라 | 없음 |
| 맥락 보존 | 낮음 — budget 초과 시 오래된 대화 완전 소실 |
| 응답 시간 | 일정 (budget 고정) |
| 면접 품질 | AI가 이전 주제를 잊음. "아까 GC 설명하셨는데" 같은 연결 질문 불가 |
| 비용 | 없음 |

**트레이드오프**: 구현이 가장 단순하고 추가 비용이 없지만, 대화가 길어지면 AI 면접관이 이전 주제에 대한 기억을 완전히 잃는다. 면접 맥락의 연속성이 끊긴다.

---

### 방안 2: 중요도 기반 선별 (Evaluation-Aware Retention)

```
[System Prompt] + [첫 질문] + [STUDY_REQUIRED 턴 원문] + [최근 5턴 원문]
```

#56에서 이미 `InterviewMessage`에 `answerLevel`(PASS, NEEDS_IMPROVEMENT, STUDY_REQUIRED)을 저장하고 있으므로, 평가 결과를 활용하여 중요한 턴만 선별 유지한다.

| 항목 | 내용 |
|------|------|
| 구현 복잡도 | 낮음~중간 — 기존 eval 데이터 활용, trimming 로직 확장 |
| 추가 AI 호출 | 없음 (기존 평가 결과 재사용) |
| 추가 인프라 | 없음 (#56에서 이미 answerLevel DB 저장) |
| 맥락 보존 | 중간~높음 — 약점 턴이 보존되어 면접 연결성 유지 |
| 응답 시간 | 일정 |
| 면접 품질 | "아까 인덱스를 잘 모르셨는데, 쿼리 최적화는 어떻게 접근하시나요?" 같은 약점 기반 꼬리질문 가능 |
| 비용 | 없음 |

**트레이드오프**: #56의 eval 인프라를 재활용하므로 추가 비용 없이 맥락 품질을 올릴 수 있다. 다만 `PASS`인 턴을 제거하면 "잘한 부분"에 대한 심화 질문 기회를 잃을 수 있고, 비동기 평가가 아직 완료되지 않은 메시지(`answerLevel == null`)에 대한 처리가 필요하다.

---

### 방안 3: 3-Layer Context (Persistent + Summary + Recent)

```
[System Prompt + 누적 요약] + [최근 5-10턴 원문]
```

히스토리가 budget을 초과할 때 AI로 요약을 생성하고, 시스템 프롬프트에 누적 저장한다. 최근 원문은 슬라이딩.

| 항목 | 내용 |
|------|------|
| 구현 복잡도 | 중간 — TokenEstimator + 요약 생성/저장/갱신 로직 |
| 추가 AI 호출 | budget 초과 시점에 1회 (요약 생성) |
| 추가 인프라 | `InterviewSession.conversationSummary` 컬럼 1개 |
| 맥락 보존 | 높음 — 핵심 정보가 요약에 보존 |
| 응답 시간 | 일정 + 요약 시점에 추가 지연 (비동기 처리 가능) |
| 면접 품질 | 요약 품질에 의존. 요약이 정확하면 전체 맥락 유지 |
| 비용 | 요약 AI 호출 비용 (세션당 2-3회) |

**트레이드오프**: 맥락 보존이 가장 우수하지만, 요약 품질을 제어할 수 없다는 근본적 리스크가 있다. AI가 "지원자가 GC를 잘 설명했다"고 요약했는데 실제로는 부정확했다면, 이후 면접관이 잘못된 전제로 질문한다.

---

### 방안 4: RAG 기반 검색 (Vector Retrieval)

```
[System Prompt] + [현재 질문과 관련된 과거 턴 검색 결과] + [최근 3-5턴 원문]
```

모든 메시지를 벡터 DB(Embedding)에 저장하고, 현재 대화와 의미적으로 관련된 과거 턴을 검색하여 포함한다.

| 항목 | 내용 |
|------|------|
| 구현 복잡도 | 높음 — 임베딩 생성 + 벡터 DB + 검색 로직 |
| 추가 AI 호출 | 매 메시지마다 임베딩 생성 1회 |
| 추가 인프라 | 벡터 DB (pgvector, Pinecone 등) |
| 맥락 보존 | 최고 — 주제별로 관련 대화를 정확히 검색 |
| 응답 시간 | 벡터 검색 지연 추가 (~50-100ms) |
| 면접 품질 | 가장 우수 — "아까 Java GC 질문에서..." 같은 정확한 참조 가능 |
| 비용 | 임베딩 API 비용 + 벡터 DB 운영 비용 |

**트레이드오프**: 기술적으로 가장 우아하지만, 면접 대화는 20-30턴 수준의 짧은 대화이므로 벡터 DB 도입이 과잉이다. 임베딩 정확도가 면접 품질을 좌우하게 되며, 인프라 비용도 높다.

---

### 방안 5: Map-Reduce 요약 (Chunked Summarization)

```
[System Prompt] + [초반 요약] + [중반 요약] + [최근 원문]
```

히스토리를 청크(5턴 단위)로 나눠 각각 요약하고, 요약들을 이어붙인다.

| 항목 | 내용 |
|------|------|
| 구현 복잡도 | 높음 — 청크 분할 + 다중 요약 + 병합 |
| 추가 AI 호출 | 청크당 1회 (5턴마다) |
| 추가 인프라 | 청크별 요약 저장 필요 |
| 맥락 보존 | 높음 — 시간순 맥락이 구간별로 보존 |
| 응답 시간 | 요약 생성 시 다중 AI 호출로 지연 |
| 면접 품질 | 양호 |
| 비용 | 높음 — 다중 AI 호출 |

**트레이드오프**: 100턴 이상의 장기 대화에 적합한 전략이다. 20-30턴 면접에서 5턴마다 요약하면 4-6회 추가 AI 호출이 발생하며, 비용 대비 효과가 방안 3(단일 누적 요약)보다 낮다.

## 기술적 의사결정

### 비교 요약

| 기준 | 방안 1 | 방안 2 | 방안 3 | 방안 4 | 방안 5 |
|------|--------|--------|--------|--------|--------|
| 구현 비용 | ★ | ★~★★ | ★★ | ★★★★ | ★★★ |
| 추가 AI 비용 | 0 | 0 | 낮음 | 중간 | 높음 |
| 맥락 보존 | ★ | ★★★ | ★★★ | ★★★★ | ★★★ |
| 면접 품질 | ★★ | ★★★ | ★★★ | ★★★★ | ★★★ |
| 기존 인프라 활용 | - | ★★★★ | - | - | - |
| 포트폴리오 차별점 | ★ | ★★★ | ★★★ | ★★★★ | ★★ |

### 채택: 방안 1 + 방안 2 조합

```
[System Prompt]
+ [첫 질문 (예약)]
+ [STUDY_REQUIRED 턴 원문 (약점 보존)]
+ [최근 5턴 원문]
```

**채택 이유:**

1. **#56의 eval 인프라 재활용** — `answerLevel`이 이미 `InterviewMessage` 테이블에 저장되어 있다. 새 인프라 없이 Context 품질을 올릴 수 있으며, "평가 시스템을 Context 관리에까지 활용했다"는 아키텍처 일관성이 확보된다.

2. **추가 비용 제로** — 방안 3/4/5와 달리 추가 AI 호출이나 인프라가 필요 없다. 기존 평가 결과를 trimming 로직에서 참조하는 것뿐이다.

3. **면접 도메인 최적화** — 면접에서 가장 중요한 건 "지원자의 약점"이다. `STUDY_REQUIRED` 턴을 우선 보존하면, AI 면접관이 약점 기반 꼬리질문을 자연스럽게 이어갈 수 있다.

4. **RAG는 현 시점에서 과잉** — 면접 대화는 20-30턴 수준이고, 벡터 DB 인프라 비용 대비 효과가 낮다.

5. **Map-Reduce는 도메인 부적합** — 면접은 짧은 대화이므로 청크 분할의 이점이 없다.

6. **요약 레이어는 후속 단계** — 방안 1+2로 성능 문제를 해결한 후, 방안 3(누적 요약)을 별도 이슈로 추가하여 맥락 보존을 더 강화할 수 있다.

### 후속 로드맵

| 단계 | 내용 | 이슈 |
|------|------|------|
| 1단계 | TokenEstimator + sliding window + 중요도 선별 | 이번 이슈 |
| 2단계 | 누적 요약 레이어 추가 (방안 3) | 별도 이슈 |
| 3단계 | 외부 데이터 품질 개선 (문서 스마트 잘라내기, GitHub 코드 분석, 공고 OCR) | 별도 이슈 |
| 4단계 | RAG 도입 (면접 데이터 축적 시) | 별도 이슈 |
